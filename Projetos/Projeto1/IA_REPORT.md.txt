Como construir um construtor em uma classe, cujos os atributos são privados?
-----------------------------------------------------------------------------------------------------------------------------

Construtor em Java com atributos privados

Em Java, um construtor é um método especial (com o mesmo nome da classe, sem tipo de retorno) usado para inicializar os atributos do objeto quando ele é criado. Mesmo que os atributos sejam private, o construtor pode acessá-los normalmente, pois está dentro da própria classe.

Exemplo básico
java
public class Pessoa {
    // Atributos privados
    private String nome;
    private int idade;

    // Construtor
    public Pessoa(String nome, int idade) {
        this.nome = nome;
        this.idade = idade;
    }

    // Getters e Setters (necessários já que os atributos são privados)
    public String getNome() {
        return nome;
    }

    public void setNome(String nome) {
        this.nome = nome;
    }

    public int getIdade() {
        return idade;
    }

    public void setIdade(int idade) {
        if (idade >= 0) {
            this.idade = idade;
        }
    }
}
Como usar
java
public class Main {
    public static void main(String[] args) {
        Pessoa p1 = new Pessoa("Ana", 25);
        System.out.println(p1.getNome()); // Ana
        System.out.println(p1.getIdade()); // 25
    }
}
Pontos importantes

1. this diferencia atributo de parâmetro
Quando o parâmetro do construtor tem o mesmo nome do atributo, o this.nome se refere ao atributo da classe, e nome (sem this) se refere ao parâmetro recebido.

2. Por que atributos são privados?
Isso é o princípio de encapsulamento: você protege os dados internos da classe e só permite acesso/modificação através de métodos controlados (construtor, getters, setters), evitando que valores inválidos sejam atribuídos diretamente.

3. Construtor sem parâmetros (default)
Você também pode ter um construtor vazio, e definir os valores depois com setters:

java
public Pessoa() {
    this.nome = "Sem nome";
    this.idade = 0;
}

4. Sobrecarga de construtores
Uma classe pode ter vários construtores com assinaturas diferentes:

java
public Pessoa(String nome) {
    this(nome, 0); // chama o outro construtor
}

Fixing a missing import causing a compile error.

O erro cannot find symbol class HardwareBasico acontece porque a classe HardwareBasico está dentro do pacote Computador, mas no seu Main.java você só importou Cliente e ProcessarPedido — faltou importar HardwareBasico.

Solução

No topo do Main.java, adicione o import que falta:

java
import Computador.Cliente;
import Computador.HardwareBasico;   // <-- faltando este
import Pedido.ProcessarPedido;

import java.util.Scanner;

Como todas as suas classes de hardware (HardwareBasico, Computador, MemoriaUSB, SistemaOperacional) estão no pacote Computador, você provavelmente vai precisar importar cada uma que for usar diretamente no Main:

java
import Computador.Cliente;
import Computador.HardwareBasico;
import Computador.Computador;
import Computador.MemoriaUSB;
import Computador.SistemaOperacional;
import Pedido.ProcessarPedido;
Por que isso acontece?

Em Java, quando você organiza classes em pacotes (pastas), cada classe só "enxerga" automaticamente as outras classes do mesmo pacote. Para usar uma classe de um pacote diferente, você sempre precisa importá-la explicitamente — mesmo que ela apareça na árvore de arquivos do projeto.

Dica extra

Se você reparar, a mensagem de erro se repete várias vezes (linhas 15, 16, 17, 18, 20...) — isso é porque o compilador encontra o mesmo problema em cada uso da classe. Corrigindo o import, esses erros devem desaparecer todos de uma vez.

Verifique também a declaração do pacote

Certifique-se de que o arquivo HardwareBasico.java (dentro da pasta Computador) começa com:

java
package Computador;

public class HardwareBasico {
    // ...
}

Se a classe não tiver package Computador; na primeira linha, mesmo estando na pasta certa, o Java não vai reconhecê-la como parte do pacote, e o import vai falhar.

Essa pasta em Java aparece assim que crio o projeto, porém, se eu remover o codigo não roda. Essa questão depende da versão do intellij Idea ou tem como remover sem afetar os pacotes?

Essa pasta java não é gerada automaticamente pela versão do IntelliJ — ela é apenas uma pasta comum que foi marcada como "Sources Root" (por isso aparece com o ícone azul). É essa marcação, e não o nome da pasta, que faz o Java/IntelliJ saber onde começar a procurar os pacotes.

Por que o projeto "quebra" se você remove a pasta

Se você simplesmente deletar/mover a pasta java sem reconfigurar o Source Root, o IntelliJ perde a referência de onde os pacotes começam, e os imports (Computador.Cliente, Pedido.ProcessarPedido, etc.) param de ser encontrados — não é sobre o código em si, é sobre a configuração do projeto.

Como resolver

Você tem duas opções:

Opção 1 — Manter a estrutura, só reorganizar visualmente

Não precisa fazer nada, o java só está aí porque foi definido como raiz de código-fonte na criação do projeto.

Opção 2 — Remover a pasta java e ajustar o Source Root manualmente
Mova as pastas Computador, Main e Pedido para um nível acima (para dentro de PCMania diretamente, por exemplo).
Clique com o botão direito na pasta java (agora vazia) → Mark Directory as → Unmark as Sources Root.
Clique com o botão direito na pasta onde os pacotes ficaram (ex: PCMania) → Mark Directory as → Sources Root.
Delete a pasta java vazia.

⚠️ Isso não afeta os pacotes (package Computador; continua igual), porque o nome do pacote só depende da estrutura de pastas dentro da Source Root, não do nome da Source Root em si.

Opção 3 (recomendada, já que você usa Maven) — Seguir o padrão Maven

Como seu projeto tem pom.xml, o Maven espera por padrão a estrutura:

src/main/java/...
src/main/resources/...

Em vez de src/PCMania/java, o ideal seria ter:

src/main/java/PCMania/Computador/...
src/main/java/PCMania/Main/...
src/main/java/PCMania/Pedido/...

Isso evita configurar manualmente o sourceDirectory no pom.xml e garante que mvn compile / mvn package funcionem sem problemas, além do IntelliJ reconhecer tudo automaticamente.

Resumindo: não é questão de versão do IntelliJ — é sobre qual pasta está marcada como raiz de código-fonte. Você pode reorganizar livremente, desde que ajuste essa marcação depois.

Como psso ajustar?

O problema é que getCapacidade() retorna só o número (double), sem a unidade de medida (GHz, GB, etc). Você tem duas formas principais de resolver:

Opção 1 — Adicionar um atributo unidade na classe HardwareBasico

Essa é a solução mais limpa, já que cada hardware pode ter uma unidade diferente (GHz para processador, GB para RAM/HD).

java
public class HardwareBasico {
    private String nome;
    private double capacidade;
    private String unidade; // "GHz", "GB", etc.

    public HardwareBasico(String nome, double capacidade, String unidade) {
        this.nome = nome;
        this.capacidade = capacidade;
        this.unidade = unidade;
    }

    public String getNome() {
        return nome;
    }

    public double getCapacidade() {
        return capacidade;
    }

    public String getUnidade() {
        return unidade;
    }
}

E na criação dos objetos:

java
hardwarePromocao1[0] = new HardwareBasico("Processador Core i5", 2200.0, "GHz");
hardwarePromocao1[1] = new HardwareBasico("Memória RAM", 8.0, "GB");
hardwarePromocao1[2] = new HardwareBasico("HD", 500.0, "GB");

No mostraPCConfigs():

System.out.println(hardwares[i].getNome() + ": " + hardwares[i].getCapacidade() + " " + hardwares[i].getUnidade());

Isso vai gerar:

Opção 2 — Deduzir a unidade pelo nome (sem alterar a classe)

Se você não quiser mudar a estrutura da classe, pode usar um if/else ou switch no próprio mostraPCConfigs():

java
for (int i = 0; i < hardwares.length; i++) {
    if (hardwares[i] != null) {

    }
}

⚠️ Essa opção funciona, mas é mais frágil — se o nome do hardware mudar ou vier de outro idioma, a lógica quebra.

Qual escolher?

A Opção 1 é a mais recomendada em POO: cada objeto carrega sua própria informação completa (nome, capacidade e unidade), sem depender de "adivinhar" nada pelo texto do nome. Isso deixa a classe mais coesa e reutilizável.
